# OpsDesk — Architecture

Status: implemented. Everything described here runs in this repository; anything that is only a design
target is marked **Reference** and kept out of the "implemented" statements.

---

## 1. Shape of the system

```
┌───────────────────────────────────────────────────────────────────────────┐
│ Browser (React 18 + Vite + TypeScript + Tailwind + Recharts)              │
│   lib/api.ts (bearer token, streaming export, blob download)              │
│   lib/store.tsx (session, role capabilities — UI mirror of backend RBAC)  │
│   workspaces/W1…W6 (six screens, one shared component set)                │
└──────────────────────────────┬────────────────────────────────────────────┘
                               │  HTTPS/JSON + text/event-stream style CSV
┌──────────────────────────────▼────────────────────────────────────────────┐
│ FastAPI application (backend/main.py)                                     │
│   routers/  auth · tickets · routing · escalations · side_conversations   │
│             analytics · exports · simulation                              │
│   api/      deps.py (serialisers + access rules) · schemas.py (Pydantic)  │
│   security.py  PBKDF2-SHA256 hashing · JWT bearer · RBAC dependency       │
├───────────────────────────────────────────────────────────────────────────┤
│ Service layer (backend/services/)                                         │
│   extraction · classifier · linking · case_brief · tickets · sla          │
│   routing · assignment · escalation · side_conversations · exports        │
│   analytics                                                               │
├───────────────────────────────────────────────────────────────────────────┤
│ SQLAlchemy 2.x models on SQLite (WAL) — 15 tables                         │
│   ai_models/saved_models/intent_pipeline.joblib (joblib artefact)         │
└───────────────────────────────────────────────────────────────────────────┘
```

One process serves the API **and** the built SPA (`backend/static`). If the build is missing, `GET /`
returns a JSON 503 with a `fix` hint instead of a blank page.

## 2. Request path

1. The browser calls `/api/*` on the same origin with `Authorization: Bearer <jwt>`.
2. `security.get_current_user` verifies signature + expiry and loads the user row; `require_roles(...)`
   enforces the role matrix **before** the handler runs.
3. The router validates the body with Pydantic, then calls a service function.
4. The service performs the domain work and writes any audit rows inside one transaction.
5. `api/deps.py` serialises the response — the browser never assembles domain objects itself.

Mutating endpoints that must be all-or-nothing (escalation, transfer, assignment) commit once at the end
of the service call; on exception the transaction rolls back and the API returns a typed error.

## 3. Module internals

### 3.1 Module 1 — intake, classification, case graph

- **Stage A — extraction** (`services/extraction.py`): regex `TBOH-\d+` plus hotel/supplier hints. When the
  `tboh_id` field is empty the description is scanned and `extraction_source` reports `DESCRIPTION`;
  otherwise `FIELD`. Only one booking id is adopted; ambiguity is reported rather than guessed.
- **Stage B — classification** (`services/classifier.py`): TF-IDF → logistic regression →
  `CalibratedClassifierCV`. Eight canonical intents. The pipeline is loaded from
  `ai_models/saved_models/intent_pipeline.joblib` at start-up; if missing, `mode` becomes `RULES` and a
  keyword rule set answers instead. The response carries the intent, calibrated probability, source
  (`ML` / `RULES`), per-class scores and reasoning lines.
- **Case graph** (`services/linking.py`): every ticket pointing at the same `booking_id` is linked through
  `ticket_links` with a `link_type` and reason, so the workspace can show one case rather than N tickets.
- **Case brief** (`services/case_brief.py`): exactly three points, generated by an extractive template over
  the case's own rows — ticket counts and dominant intents, booking value/status/threads, travel urgency
  with the governing SLA rule. It never invents a fact the database does not contain, and the response
  lists the ticket ids, message count and conversation count that were used.

### 3.2 Module 2 — routing

```
score = 35*RegionMatch + 25*ShiftMatch + 25*(SkillRank/5)*UrgencyWeight + 15*(1 - ActiveLoad/MaxCapacity)
```

Order of operations:

1. **Candidate pool** — users with role `OPS_AGENT` only. Escalation managers and the ops lead are never
   scored (including them was a real bug found by journey B, and is asserted in the tests).
2. **Hard filters** — offline, at capacity (`active_load >= max_capacity`), outside shift window, skill
   rank `< 4` for `CRITICAL` / `AT_RISK` / `BREACHED`, and regional eligibility
   (`APAC ↔ MEA`, `EU ↔ AMER`). Every excluded agent is returned with its reason.
3. **Score** — the four weighted terms; `UrgencyWeight` saturates at 1.0 for at-risk/breached tickets.
4. **Tie-break** — highest score → lowest active load → lowest agent id.
5. **Persist** — a `routing_audits` row holding every candidate, every component, the exclusions, the
   selected agent and the human-readable reason. Audits are append-only; a manager override creates a new
   row with the actor, never an edit.

### 3.3 Module 3 — conversations and transfer safety

- Main thread: `messages` with `PUBLIC_REPLY` (agency-visible) or `INTERNAL_NOTE` (excluded from the
  agency view — enforced by the serialiser, not by hiding a button).
- Side conversations: `side_conversations` + `side_messages`, each with its own `explicit_recipients`
  array and `created_by_group`. A supplier thread and a finance thread on the same ticket never share
  recipients.
- Transfer: changes `queue` and `assigned_user_id` only, writes a `ticket_transfers` row with
  `preserved_side_conversations` and `preserved_recipients`, then re-reads the conversations and returns
  `recipients_unchanged`. The destination group's addresses are never appended.

### 3.4 Module 4 — SLA and escalation

```
EffectiveSLADueAt = MIN(PriorityDeadline, LCD - 2h, CheckIn - 4h)
```

- Priority windows: CRITICAL 1h · HIGH 4h · MEDIUM 12h · LOW 24h.
- `governing_rule` names which term won, so the UI can explain the clock.
- `AT_RISK` at 75 % elapsed; inside a regional holiday window the threshold drops to 50 % and
  `holiday_adjustment_applied` is recorded on the ticket.
- Missing dates are listed in `missing_dates`; a travel deadline already in the past sets
  `expired_travel_deadline` and the term is ignored rather than replaced with zero.
- Storage is aware UTC (`TZDateTime` rejects naive datetimes); the API also returns
  `check_in_local` / `lcd_local` rendered in the booking's IANA timezone.
- Escalation: validates a reason, selects the eligible manager for the region, sets status `ESCALATED`,
  queue `ESCALATION_MANAGER`, reassigns ownership, writes `escalated_by` / `escalated_at` and appends an
  immutable `ESCALATED` timeline event — atomically.

### 3.5 Module 5 — product intelligence

`services/analytics.py` computes over stored rows: intent distribution, supplier complaint volume, weekly
trends, resolution-time histogram, refund bottlenecks (open count, mean open age, oldest open ticket),
regional performance, inventory/rate-sync cluster. Theme extraction tags recurring language and persists
`theme_tags`. Bug suggestions group tickets by `(supplier, intent)`, require at least three in the window
and return the frequency, period, evidence lines and a suggested action. Accepting a suggestion creates a
`product_bugs` row **in this database** — no external tracker is contacted.

### 3.6 Module 6 — exports

`POST /api/exports/stream` returns a `StreamingResponse` over a generator that yields rows in batches of
5,000. The job row is created before the first byte so progress and failures are observable. Duration is
measured around the generator, file size from the written file, throughput from rows/duration, and peak
memory by sampling `VmRSS` (a `ru_maxrss` delta under-reports on a warm process; `tracemalloc` distorted
throughput and was rejected). `GET /{uuid}/validate` re-reads the artefact and compares row and column
counts — the UI shows that result rather than a client-side guess.

## 4. Frontend architecture

- `lib/api.ts` — single fetch wrapper: bearer token, typed errors, `streamExport()` with per-chunk
  progress, `downloadExport()` via blob (an `<a href>` cannot carry the token).
- `lib/store.tsx` — session context, identity switcher, and `ROLE_CAPABILITIES`, which mirrors the backend
  role matrix so the navigation never offers a screen the API will refuse.
- `lib/hooks.ts` — `useFetch` (with optional polling), `useDebounced`, `useTicker` for countdowns.
- `components/` — `ui.tsx` (badges, KPI cards, modals, SLA cell, tabs), `charts.tsx` (Recharts wrappers
  used by all visualisations), `layout.tsx` (sidebar, top bar, identity switcher).
- SLA countdowns recompute from the absolute `effective_due_at` returned by the API, so a page left open
  does not drift; the queue itself refreshes every 60 s.

## 5. Data-access rules

- Agency requesters only see their own agency's tickets (`ensure_ticket_access`).
- Ops roles see their region; the ops lead sees everything.
- Internal notes are stripped from requester payloads in the serialiser.
- Every mutation that changes ownership or classification appends to `activity_timeline`.

## 6. Failure behaviour

| Situation | Behaviour |
| --- | --- |
| Model file missing | Classifier reports `mode: RULES`, endpoint keeps working |
| SPA build missing | `GET /` → 503 JSON with a `fix` hint (no blank page) |
| Export interrupted | Job row marked `FAILED` with the error message |
| Invalid transition (e.g. transfer to the same queue) | 422 with a specific message |
| Naive datetime passed to the SLA engine | `ValueError` — never silently coerced |
| Journey replay after state changes | `?reseed=true` restores the seeded baseline first |

## 7. Reference architecture (not implemented)

Hot/warm/cold storage tiering, DuckDB/ClickHouse analytics, Parquet on S3 and horizontal workers are
design targets documented in [`Storage_Architecture.md`](Storage_Architecture.md). This build runs a
single SQLite database on one process; DuckDB is declared in `requirements.txt` as an optional analytics
dependency and is not on the request path.


## 9. Agent layer (v2.1)

`backend/agents/` adds a supervised multi-agent layer on top of the deterministic core:

```
backend/agents/runtime.py       Agent base class, ToolSpec/ToolBox, trace records
backend/agents/tools.py         10 read-only tool adapters over existing services
backend/agents/specialists.py   8 specialist agents
backend/agents/orchestrator.py  swarm execution, plan derivation, persistence, telemetry
backend/routers/agents.py       /api/agents/* surface
```

Design constraints: tools are read-only (no agent can post, reassign, escalate or create a
record); every agent declares its allow-list and unknown names fail at import; a raising agent
degrades to `ERROR` without failing the run; every review is stored in `agent_runs` with the
full per-agent trace and the derived plan. See `documentation/Agent_Architecture.md`.

## 10. Operational surface (v2.1)

| Concern | Implementation |
| --- | --- |
| Tracing | `X-Request-ID` (generated or propagated) + `X-Response-Time-Ms` on every response, JSON access log line per request |
| Metrics | `GET /api/metrics` in Prometheus text format: request counters per route/status class, latency quantiles, rate-limit counter, live ticket/booking/user gauges |
| Probes | `GET /api/health` (liveness), `GET /api/ready` (DB + classifier + export dir, 503 when degraded) |
| Abuse control | Fixed one-minute window per client on `/api/auth/login` and `/api/auth/demo-login`, `Retry-After` on 429, `OPSDESK_RATE_LIMIT_PER_MINUTE=0` disables |
| Headers | `nosniff`, `Referrer-Policy`, `Permissions-Policy`, CSP locked to same-origin (no `frame-ancestors`, so preview panes keep working) |
| Storage | Idempotent hot-path indexes created at startup (`tickets(status,queue)`, `tickets(assigned_user_id,status)`, `messages(ticket_id,created_at)`, `agent_runs(ticket_id,created_at)`, …) |
| Packaging | `Dockerfile` (multi-stage, non-root, healthcheck), `docker-compose.yml` (SQLite default, Postgres profile), `Makefile`, GitHub Actions CI, `scripts/backup_db.py` |
