# OpsDesk for TBO — Final Summary

**Track 1 · booking-centric replacement for ticket-centric travel operations**

Everything below exists in this repository and was executed on this build. Figures are read from the
artefacts in `benchmark_results/`, `ai_models/evaluation/` and the crawl report — not typed by hand.

---

### 1. What was built

A working B2B travel-ops platform, not a click-through prototype: 49 synthetic tickets across 12 bookings,
4 agencies and 16 users, served by a FastAPI application that also serves the compiled React SPA, backed by
15 SQLAlchemy tables in SQLite (WAL) and a scikit-learn intent pipeline persisted with joblib.
Six workspaces expose the six modules; every screen reads live API data.

### 2. The thesis, implemented rather than stated

The booking is the join key. A ticket without a booking field still lands on the right case, because Stage A
extracts `TBOH-\d+` from the message and `ticket_links` rebuilds the case graph — Journey A proves it by
raising a refund ticket on `TBOH-778899` with the field left empty and ending up linked to
`TCK-101/104/109` with a three-point brief.

### 3. Modules 1–6, all functional

Intake and classification (8 canonical intents, calibrated, rule fallback, template-disjoint holdout
**0.8958 accuracy / 0.8964 macro F1**, n=288) · routing (`35/25/25/15`, five hard filters, tie-break,
append-only audit, manager override) · conversations (main thread plus independent side conversations with
immutable recipients and verified transfer safety) · SLA and escalation
(`MIN(priority, LCD−2h, check-in−4h)`, holiday threshold 75 % → 50 %, live countdowns, atomic escalation with
real ownership) · product intelligence (intents, suppliers, refund bottleneck, themes, recurring-pattern bug
proposals with evidence) · governance exports (real `StreamingResponse`, batch 5,000, measured metrics,
on-disk validation).

### 4. Six workspaces, no dead ends

W1 queue & SLA command center · W2 three-pane case workspace · W3 routing & capacity studio · W4 escalation
war room · W5 intelligence & governance hub · W6 live simulation lab. A headless Chromium crawl opened all
six, exercised posting a note, a side-conversation transfer, an escalation, a routing decision, a
50,000-row export and two role switches: **19 screenshots, 0 console errors, 0 HTTP errors**.

### 5. Five seeded journeys, executed end-to-end

`python -m simulation.run_all` → **5/5 journeys, 34/34 steps** against the live API, including the
why-not-FIFO explanation in Journey B (5 eligible / 4 excluded, winner 94.375/100 on load 1/8) and the
50,000-row export with validation in Journey E. A single journey run reseeds the baseline first, so results
are reproducible rather than dependent on accumulated state.

### 6. Measured performance, not promises

Export of **50,000 rows · 25 columns · 16.31 MB** in **≈1.2 s** at **≈39,000 rows/s** with peak memory
under 35 MB; routing comparator median **3.9 ms** (p95 ≈4.2 ms); queue/analytics endpoints in the 3–18 ms
range; classifier calls ≈2 ms. All figures are regenerated by `python -m scripts.run_benchmark` and feed the
decks directly.

### 7. Tests that were actually run

**106 automated tests pass** (`pytest tests backend/tests`), including the seven mandatory routing cases, the
SLA edge cases (missing/expired dates, holiday threshold, UTC enforcement), conversation isolation and
transfer preservation, escalation semantics, export integrity and RBAC. `documentation/Testing_Report.md`
lists Expected / Actual / Pass-Fail for every check and has a separate **"Not executed"** section — nothing
untested is marked as passing.

### 8. Fourteen visualisations from real rows

SLA mix, weekly volume, region × SLA, intent volume, calibrated class scores, agent reference scores,
load-vs-score, escalation trend, war-room region mix, deadline pressure, intent distribution, supplier
complaints, weekly trend and resolution-time distribution — each fed by an API payload, each with tooltips,
and with server-side filters and a 7/30/90/365-day window on the analytics views.

### 9. Presentations and video

`presentations/` holds a **12-slide Executive_Pitch_Deck** and a **15-slide Technical_Architecture_Deck** in
both PPTX (editable native shapes) and PDF, 16:9 light theme, ending on the exact required line — *"OpsDesk
does not just manage tickets. It understands the entire travel operation."* — built from real screenshots
by `scripts/generate_presentations.py`. `videos/` holds a **105-second Explainer** (7 scenes) and a
**3 min 27 s Product_Demo** (6 segments) recorded by Playwright and assembled with FFmpeg, plus both SRT
tracks and the storyboard, voiceover, shot-list and production-guide documents.

### 10. Limitations, stated instead of hidden

Synthetic dataset only (labelled in the UI, the API and every document); no external integrations — no
Jira, no supplier APIs, no email delivery, and the product says so; single-node SQLite with the
hot/warm/cold tiering documented as reference architecture in `documentation/Storage_Architecture.md`;
PostgreSQL, DuckDB, cross-browser, mobile and accessibility checks listed as **NOT RUN**; the videos ship
without audio by design, with scripts provided for a human voiceover and the exact `ffmpeg` command to mux
it. The demo password is a synthetic seed value, overridable by environment variable and disabled entirely
with `OPSDESK_ENABLE_ROLE_SWITCH=false`.

## v2.1 — agent mesh and production hardening

11. **Eight specialist agents, not one chatbot.** `backend/agents/` runs intake, SLA-risk,
    routing-advisor, escalation, communications, QA/leakage, product-intelligence and playbook
    reviewers over a case. Each declares a read-only tool allow-list over the same services the
    REST API uses, each step is traced with arguments and timings, and every review is stored in
    `agent_runs`. Measured: **24–56 ms** per eight-agent review, **5 plan actions** on `TCK-101`.
    No external model is contacted (`external_model: null`; `OPSDESK_LLM_ENDPOINT` is a
    documented but unused extension point), so nothing here claims a capability it lacks.
12. **Operational surface.** `/api/ready` (DB + classifier + export dir), `/api/metrics`
    (Prometheus text from measured counters), `X-Request-ID` / `X-Response-Time-Ms` on every
    response with a JSON access log, per-client rate limiting on sign-in with `Retry-After`,
    security headers that keep preview embedding working, and hot-path indexes created
    idempotently at startup.
13. **Deployable.** Multi-stage `Dockerfile` (non-root, healthcheck), `docker-compose.yml` with
    a Postgres profile, `Makefile`, GitHub Actions CI and a consistent SQLite backup script.
14. **Verification.** `pytest tests backend/tests -q` → **121 passed** (15 new tests covering
    agent grounding, containment, RBAC, telemetry, probes, metrics and the limiter), five
    journeys still 5/5, and the W2 Agent mesh run verified inside a sandboxed iframe with zero
    console errors.
