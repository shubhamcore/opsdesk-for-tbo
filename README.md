# OpsDesk for TBO

**Track 1 — a booking-centric replacement for ticket-centric travel operations.**

> A booking is the operational context. A ticket is only one interaction associated with that booking.

OpsDesk is a working enterprise B2B travel-ops platform: React + Vite + TypeScript in the browser,
FastAPI + SQLAlchemy + Pydantic behind it, a scikit-learn intent pipeline, and a SQLite (WAL) database
that is Postgres-compatible by design. Everything in the product runs against the database — there are
no mock screens, no hardcoded confidences and no simulated progress bars.

**All agencies, bookings, passengers and tickets in this environment are synthetic.** The dataset is
generated by `database/seed_data/seed.py` and labelled as synthetic in the UI, the API (`data_notice`)
and every report in this repository. No real TBO customer data is present.

---

## What it does

| Module | What is implemented |
| --- | --- |
| 1 · Intake & understanding | Stage A regex extraction of `TBOH-\d+`, Stage B calibrated 8-intent classifier, booking-first case graph, evidence-bound 3-point case brief |
| 2 · Routing | Hard filters → `35*RegionMatch + 25*ShiftMatch + 25*(SkillRank/5)*UrgencyWeight + 15*(1-ActiveLoad/MaxCapacity)`, tie-break, persisted breakdown, immutable audit, manager override |
| 3 · Conversations | Main thread (public replies + internal notes) and independent side conversations with immutable explicit recipients; transfer-safe verification |
| 4 · SLA & escalation | SLA matrix, `MIN(priority, LCD−2h, check-in−4h)`, holiday-adjusted at-risk threshold, live countdowns, first-class escalation with real ownership |
| 5 · Product intelligence | Intent/supplier/regional analytics, refund bottlenecks, theme extraction, recurring-pattern bug suggestions with evidence |
| 6 · Governance exports | 50,000-row streamed export through a real `StreamingResponse`, measured duration/throughput/memory, on-disk validation, job tracking |

Six workspaces expose it: **W1** Ops Queue & SLA Command Center · **W2** Unified Ticket & Booking Case
Workspace · **W3** Routing & Agent Capacity Studio · **W4** Escalation Manager War Room ·
**W5** Product Intelligence & Governance Hub · **W6** OpsDesk Live Simulation Lab.

## Agent mesh (v2.1)

Eight specialist reviewers run over one case on demand — each restricted to an explicit,
read-only tool allow-list over the same services the API uses, each step traced and persisted.
They propose; they never mutate a case. No external model is called (`external_model: null` in
every payload, `OPSDESK_LLM_ENDPOINT` is a documented but unused extension point).

| Agent | Owns the question | Output on `TCK-101` |
| --- | --- | --- |
| Intake & Classification | What is this case? | Refund Delay · 81.2% confidence · 10 tickets in case |
| SLA & Travel Deadline Risk | How much time is left? | BREACHED · `PRIORITY_SLA` · 28,565 min past due |
| Routing & Capacity Advisor | Who should own it? | Ananya Sharma · 63.12/100 |
| Escalation Readiness | Does it need an EM? | Escalate to an EM · 2 eligible |
| Customer Communications | What do we say? | Reply draft from 3 thread messages |
| Quality & Leakage Guard | What must not get out? | 0 policy risks |
| Product Intelligence | Pattern or incident? | Hotelbeds × Refund Delay recurs 6× |
| Resolution Playbook | What is the SOP? | 3 authored steps |

Run it from **W2 → Agent mesh**, or `POST /api/agents/cases/TCK-101/run`. Measured: **24–56 ms**
per full review, **5 plan actions** on a breached case. Details: `documentation/Agent_Architecture.md`.

## Quick start

```bash
# 1 — dependencies
python -m pip install -r requirements.txt
cd frontend && npm install && npm run build && cd ..   # builds into backend/static

# 2 — seed the synthetic dataset (49 tickets, 12 bookings, 16 users, 4 agencies)
python -m database.seed_data.seed

# 3 — run (serves both the API and the built SPA)
uvicorn backend.main:app --host 0.0.0.0 --port 8000

# 4 — open
#     http://localhost:8000          → app
#     http://localhost:8000/docs     → OpenAPI
```

Sign in with a seeded identity, e.g. `nisha.verma@tbo.com` (Ops Lead). The demo password is printed by
`GET /api/auth/identities` (`demo_password_hint`) and is set by `OPSDESK_DEMO_PASSWORD`; it is **not** a
real credential. One-click demo sign-in is available on the login screen while
`OPSDESK_ENABLE_ROLE_SWITCH=true`.

## Production shape

```bash
make install          # python + frontend deps
make seed             # synthetic dataset
make serve            # uvicorn on :8000
make verify           # 121 tests + five journeys (release gate)

docker build -t opsdesk-tbo:2.1.0 .   # multi-stage image, non-root, healthcheck on /api/ready
docker compose up -d                  # SQLite on a volume; Postgres profile available
```

Operational endpoints: `GET /api/health` (liveness), `GET /api/ready` (readiness, 503 when
degraded), `GET /api/metrics` (Prometheus text from measured counters). Every response carries
`X-Request-ID` and `X-Response-Time-Ms`; sign-in is rate limited per client with `Retry-After`.
See `documentation/Deployment_Guide.md` and `documentation/Agent_Architecture.md`.

## Limitations, stated plainly

- **No external integrations.** No Jira, no supplier APIs, no email delivery. Side conversations record
  messages in the database; the UI says so. Bug suggestions create local records only.
- **Synthetic data only.** The classifier is trained on template-generated text, so its 0.8958 holdout
  accuracy is a measure of that corpus, not of TBO production traffic.
- **Single node.** SQLite in WAL mode on one process. The hot/warm/cold tiering in
  `documentation/Storage_Architecture.md` is a documented reference architecture, not deployed.
- **Explainer narration.** `videos/Explainer.mp4` is a real 105-second video built from rendered scene
  cards and product screenshots with a matching SRT; the voiceover script is provided for a human
  recording, and the production guide has the exact `ffmpeg` command to mux it in.
- **Demo password.** Documented and overridable by environment variable; disable demo sign-in with
  `OPSDESK_ENABLE_ROLE_SWITCH=false` for any shared deployment.
- **Sandboxed preview frames.** When the SPA is embedded in a sandboxed iframe (`allow-scripts`
  without `allow-same-origin`), browsers throw a `SecurityError` on any `localStorage` access. All
  token/user persistence goes through a shim in `frontend/src/lib/api.ts` that falls back to an
  in-memory store, so the app boots and behaves normally there; the session then lasts for the
  lifetime of the frame rather than surviving a reload.
